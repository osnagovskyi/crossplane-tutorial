# Azure intro with Blob Storage, PostgreSQL, and Workload Identity

[`../../examples/azure-intro-blob.yaml`](../../examples/azure-intro-blob.yaml) contains one ClusterClaim selecting `cluster-azure-blob`. That composition provisions AKS, Blob Storage, and an Entra-only PostgreSQL Flexible Server together. It reuses the cluster name from `azure-intro.yaml`, so it is an alternative configuration of that cluster, not a second independent environment.

The new example no longer includes the legacy password Secret, PostgreSQL 11 SQLClaim, or `silly-demo` AppClaim. They remain in the original `azure-intro.yaml`. Applying the new file with ordinary `kubectl apply` does not delete legacy resources that were previously created.

The infrastructure manifest prepares workload identity federation and the database setup administrator. **PostgreSQL row access for the app is completed by the demo-app Helm setup Job**, which creates the Entra database role, table, and SQL grants. The composition generates the chart values; it does not install that chart itself.

The composition is a snapshot of the installed `cluster-azure` composition from `dot-kubernetes:v0.12.45`, preserving its AKS, Cilium, provider configurations, and optional application steps. It adds:

- AKS OIDC issuer and Workload Identity enablement.
- A Standard LRS StorageV2 account in the cluster resource group (`eastus`). Its 24-character name is derived from the composite UID to avoid global naming conflicts.
- A private container named `demo` (public network endpoint, no anonymous blob access).
- A user-assigned managed identity and a federated identity credential using the observed AKS issuer.
- **Storage Blob Data Contributor** scoped to that container, using the identity's principal ID, not its client ID.
- An Entra-only PostgreSQL 16 Flexible Server (B1ms, 32 GiB) and a database named `demo`. Password authentication is disabled.
- A separate managed identity/federation for the database setup Job, configured as the PostgreSQL Entra administrator. The app continues to use the **same original identity** for blob and database requests.
- A `blob-demo` namespace and `blob-demo-values` ConfigMap on AKS. The generated Helm values include storage URL, database host, application identity IDs, and setup identity IDs; no secrets or tokens.

The app federated subject is `system:serviceaccount:blob-demo:demo-blob-demo`, matching Helm release **demo**, namespace **blob-demo**, and the service account generated by `demo-app/charts/blob-demo`. The chart adds the client-ID annotation and workload-identity pod label. The setup Job uses `system:serviceaccount:blob-demo:demo-blob-demo-db-bootstrap`. Keep those release/namespace names, or update both subjects in the composition when changing them.

The database firewall's `0.0.0.0` rule allows Azure-origin traffic, including other Azure subscriptions; Entra authentication is still mandatory. This is a demo networking choice. Use restricted egress IP rules or private networking for a production deployment.

## Provision the resources

Run from `crossplane-tutorial`, against the **management** cluster. The ClusterClaim/CompositeCluster definition, AKS, Helm and Kubernetes providers, composition functions, and Azure ProviderConfig `default` must already exist. This example does not require SQLClaim or AppClaim definitions. The installed functions used here are patch-and-transform, go-templating, and auto-ready.

The Azure provisioning identity needs permission to create storage accounts, containers, managed identities, PostgreSQL Flexible Servers/databases/firewall rules, and PostgreSQL Entra administrators, plus `Microsoft.Authorization/roleAssignments/write` at the target scope (for example Owner, or Contributor plus Role Based Access Control Administrator). The app receives blob data permissions plus PostgreSQL `CONNECT`, schema `USAGE`, and table `SELECT`, `INSERT`, `UPDATE`. A Helm Job applies the SQL grants; an Azure role assignment alone does not grant PostgreSQL row access.

```sh
kubectl apply -f providers/azure-blob.yaml
kubectl wait --for=condition=Healthy --timeout=600s \
  provider.pkg.crossplane.io/upbound-provider-azure-storage \
  provider.pkg.crossplane.io/upbound-provider-azure-managedidentity \
  provider.pkg.crossplane.io/upbound-provider-azure-authorization \
  provider.pkg.crossplane.io/upbound-provider-azure-dbforpostgresql
kubectl apply -f compositions/cluster-azure-blob/composition.yaml
kubectl apply -n a-team -f examples/azure-intro-blob.yaml
kubectl wait -n a-team --for=condition=Ready clusterclaim/cluster-01 --timeout=1800s
```

The four data-service providers are pinned to **v2.7.2**, matching the Azure family installed in the current management cluster. If your installation uses another provider version, align the versions before applying. The provider manifest explicitly includes PostgreSQL, using the current `FlexibleServer/v1beta2` API; the legacy SQL configuration package is not required.

If `cluster-01` is already bound to another composition, inspect the claim and its CompositeCluster before switching. A claim/composite pinned to a composition revision or using Manual update policy may require explicitly selecting the new composition/revision on the bound CompositeCluster. Do not delete/recreate the cluster to enable Workload Identity. Do not keep both intro files under GitOps management of the same claim.

## GitOps location

`argocd/apps.yaml` watches `a-team/`, which currently contains only the composition definition. Installing a Composition registers a blueprint; it does not provision resources without a claim. The example under `examples/` is outside that watched path. Apply it with the command above, or deliberately include the claim and provider prerequisites in your GitOps configuration. Keep `a-team/composition.yaml` synchronized with the canonical composition if managing that copy with Argo CD.

## Deploy the browser app on AKS

Retrieve the AKS kubeconfig into a separate local file. It is a credential: keep the file outside the repository and restrict access.

```sh
umask 077
kubectl -n a-team get secret cluster01-cluster \
  -o jsonpath='{.data.kubeconfig}' | base64 --decode > /tmp/cluster01-kubeconfig

kubectl --kubeconfig /tmp/cluster01-kubeconfig -n blob-demo \
  get configmap blob-demo-values -o jsonpath='{.data.values\.yaml}' \
  > /tmp/blob-demo-values.yaml
```

Build/push the image for the AKS node architecture (the default nodes are amd64). Replace `YOUR_REGISTRY` with a registry reachable by AKS and configure image-pull access if it is private. Workload Identity for blob access does not grant container image-pull access.

```sh
cd ../demo-app
docker buildx build --platform linux/amd64 \
  -t YOUR_REGISTRY/blob-demo:0.2.0 --push .
helm upgrade --install demo ./charts/blob-demo \
  --kubeconfig /tmp/cluster01-kubeconfig \
  --namespace blob-demo \
  --values /tmp/blob-demo-values.yaml \
  --set image.repository=YOUR_REGISTRY/blob-demo \
  --wait --wait-for-jobs --timeout 25m
kubectl --kubeconfig /tmp/cluster01-kubeconfig -n blob-demo \
  port-forward svc/demo-blob-demo 8080:80
```

Open http://localhost:8080, upload/download a file, then save/read a database row. Stop the local Docker demo first if it still owns port 8080, or forward `8081:80` instead. No storage account key or database password is passed to the app. It requests PostgreSQL access tokens using its existing workload identity, with TLS certificate/hostname verification.

Helm also starts an idempotent setup Job using the separate Entra administrator identity. It maps the app identity's principal ID to PostgreSQL role `demo_app`, creates `demo.rows`, and grants only the required row privileges. The app never receives the setup identity. The completed Job stays in the release; an image tag, chart version, or database configuration change creates a replacement Job. The generated ConfigMap waits for the database hostname and identity IDs, while cluster claim readiness includes the administrator and federation resources. Permission propagation and setup can take several minutes; app readiness waits for the table to become accessible.

For an existing blob-only installation: apply the updated composition, let the claim adopt its new revision (Automatic update policy), fetch `blob-demo-values` again, build/push image `0.2.0`, and run the Helm upgrade. A Manual revision policy requires explicitly selecting the new revision. If setup exhausts its retries, inspect its logs, fix the cause, delete the failed Job, and rerun Helm.

## Validation and troubleshooting

Validation covers initial/observed-state template rendering, generated Helm values, both federated service-account subjects, unit tests for database token use and SQL behavior, and local PostgreSQL/Azurite integration. Server dry-run checks use the installed PostgreSQL CRDs. The simplified example requires only the ClusterClaim definition; it no longer references the legacy SQLClaim/AppClaim APIs. These changes do not provision Azure resources until applied, and local password-based PostgreSQL cannot validate a live Entra token exchange.

```sh
# Management cluster:
kubectl get kubernetesclusters.containerservice.azure.upbound.io cluster01 \
  -o jsonpath='{.status.atProvider.oidcIssuerUrl}'
kubectl get accounts.storage.azure.upbound.io,containers.storage.azure.upbound.io
kubectl get userassignedidentities.managedidentity.azure.upbound.io
kubectl get federatedidentitycredentials.managedidentity.azure.upbound.io
kubectl get roleassignments.authorization.azure.upbound.io
kubectl get flexibleservers.dbforpostgresql.azure.upbound.io
kubectl get flexibleserveractivedirectoryadministrators.dbforpostgresql.azure.upbound.io
# AKS:
kubectl --kubeconfig /tmp/cluster01-kubeconfig -n blob-demo get pods
kubectl --kubeconfig /tmp/cluster01-kubeconfig -n blob-demo logs deployment/demo-blob-demo
kubectl --kubeconfig /tmp/cluster01-kubeconfig -n blob-demo logs -l app.kubernetes.io/component=db-bootstrap
```

If a resource fails, inspect its `Synced` condition with `kubectl describe`. The role and federation resources appear only after Azure reports the necessary principal ID/account ID and OIDC issuer. The ConfigMap can become available before Azure permissions finish propagating. As with the base tutorial, deleting the cluster claim deletes its composed Azure resources, including this storage account and its blobs, plus the new PostgreSQL server and rows.
